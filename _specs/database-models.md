# Spec for Database Models

branch: claude/feature/database-models

## Summary
Implement SQLAlchemy ORM models for the three core entities: Client, Publication, and Alert. These models form the foundation of the ReguLens data schema, enabling storage of client profiles, scraped regulatory publications, and AI-generated alerts linking publications to affected clients.

**Note**: This spec implements the exact database schema defined in MVP-PLAN.md section "Database Models (MVP Schema)". No deviations from the planned schema should be made without updating the MVP plan first.

## Functional Requirements

### Client Model
- Represents tax professional's clients (entities being monitored)
- Fields:
  - `id`: UUID primary key
  - `name`: Client identifier/code (e.g., TECH_001)
  - `entity_type`: Business structure (C-Corp, S-Corp, LLC, Partnership, Sole Prop)
  - `industry`: Industry description
  - `industry_naics`: NAICS code (optional)
  - `ca_nexus`, `tx_nexus`, `fl_nexus`: Boolean flags for state nexus (CA/TX/FL)
  - `revenue_range`: Revenue bracket (<1M, 1-10M, 10-50M, 50M+)
  - `tax_credits_used`: Array of tax credits (R&D, Film, Other)
  - `created_at`, `updated_at`: Timestamp tracking
- Relationship: One-to-many with Alert model
- Data source: Loaded from CSV file (100 sample clients for MVP)

### Publication Model
- Represents scraped regulatory documents/announcements
- Fields:
  - `id`: UUID primary key
  - `title`: Publication title
  - `state`: Jurisdiction (CA, TX, FL)
  - `source`: Source identifier (e.g., "CA FTB Newsroom")
  - `url`: Publication URL
  - `content`: Full text or summary of publication
  - `published_date`: When publication was issued
  - `scraped_at`: When ReguLens scraped it
  - `processed`: Boolean flag indicating AI processing complete
- Relationship: One-to-many with Alert model
- Data source: Populated by web scrapers

### Alert Model
- Links Publications to affected Clients with AI analysis
- Fields:
  - `id`: UUID primary key
  - `publication_id`: Foreign key to Publication
  - `client_id`: Foreign key to Client
  - `summary`: 2-3 sentence AI-generated summary
  - `affects_client`: Impact determination (YES, MAYBE, NO)
  - `impact_level`: Severity (HIGH, MEDIUM, LOW)
  - `explanation`: Why publication affects this client
  - `action_items`: Array of recommended actions
  - `reasoning`: AI reasoning/justification
  - `email_sent`: Boolean flag for delivery tracking
  - `reviewed`: Boolean flag for user acknowledgment
  - `created_at`: Alert creation timestamp
- Relationships:
  - Many-to-one with Publication
  - Many-to-one with Client
- Data source: Generated by AI matching process

### Model Module Organization
- Each model in separate file: `models/client.py`, `models/publication.py`, `models/alert.py`
- Central import in `models/__init__.py` for easy access
- All models inherit from SQLAlchemy `Base` (defined in `database.py`)

## Possible Edge Cases

### Data Integrity
- UUID generation must work correctly across all models
- Foreign key constraints must prevent orphaned alerts
- Array fields (tax_credits_used, action_items) must handle empty arrays
- Optional fields (industry_naics, content) must allow NULL
- Timestamp fields must use timezone-aware datetime

### Model Relationships
- Publication can have zero or many alerts (one pub may affect multiple clients)
- Client can have zero or many alerts (one client may be affected by multiple pubs)
- Alert must always reference valid publication and client (required foreign keys)
- Cascading deletes must be considered (what happens if client/publication deleted?)

### Database Migration
- Models must be compatible with Alembic autogenerate
- Column types must map correctly to PostgreSQL types
- UUID field must use PostgreSQL UUID type (not string)
- ARRAY fields must use PostgreSQL-specific types
- Default values and server defaults must be properly configured

### Import and Usage
- Models must be importable from `backend.app.models`
- Base class must be shared across all models
- SQLAlchemy relationships must be bidirectional where needed
- Models should work with FastAPI dependency injection

## Open Questions

- Should we add soft delete functionality (deleted_at field) instead of hard deletes?
- Do we need indexes on frequently queried fields (state, processed, reviewed)?
- Should publication.content have a length limit or be unlimited TEXT?
- Do we need cascade delete behavior, or should deletes be blocked if relationships exist?
- Should we add unique constraints (e.g., client.name must be unique)?
- Do we need audit fields (created_by, updated_by) for future multi-user support?

## Testing Guidelines

Create test file(s) in the ./tests folder for the new feature, and create meaningful tests for the following cases, without going too heavy:

### Model Instantiation Tests
- Test creating Client instance with all required fields
- Test creating Publication instance with all required fields
- Test creating Alert instance with all required fields and foreign keys
- Test UUID auto-generation on model creation
- Test default values are applied correctly (booleans, arrays, timestamps)

### Field Validation Tests
- Test nullable vs non-nullable fields
- Test ARRAY fields accept list inputs
- Test DateTime fields accept timezone-aware datetime objects
- Test foreign key references work correctly

### Relationship Tests
- Test Alert.publication relationship returns Publication instance
- Test Alert.client relationship returns Client instance
- Test Publication.alerts returns list of alerts
- Test Client.alerts returns list of alerts
- Test bidirectional relationships work

### Database Integration Tests
- Test models can be committed to database
- Test querying models from database works
- Test relationships work across database queries
- Test UUID primary keys work correctly
- Test foreign key constraints are enforced

### Import Tests
- Test models can be imported from `backend.app.models`
- Test all three models are available in module namespace
- Test Base is correctly inherited
